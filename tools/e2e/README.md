# Живые проверки админки (треки Ж и З)

Скрипты, которыми закрывались спринты Ж0–Ж8 (ADMIN.md, «Критерий» у каждого спринта) и
закрываются итерации трека З (OWNER.md, раздел «Трек З» ниже).
Они гоняются против **живого стенда**: поднятый сервер, Postgres с миграциями и сид с
известными пользователями. Юнит-тесты Go живут рядом с кодом (`go test ./...`) — здесь
только то, что проверяет стойку целиком: API + база + браузер.

Два вида скриптов:

- `e2e_*.py` — API-уровень (python3 + `psql`): деньги, инварианты, гонки, клубные сутки,
  посадка на офлайн-шелл, касса, табло и компания. Ходят в `/api/v1`, смотрят в базу
  напрямую, при необходимости поднимают `mock_agent.js` (мок агента ПК на `/ws/shell`; третий аргумент — файл с
  сообщением агента, мок шлёт его при подключении и при каждой смене файла — `agent_start(pc, send=…)` в `_z.py`).
- `pw_*.js`, `smoke_*.js` — браузер (playwright-core + Chromium): admin.html, киоск и PWA
  как их видит админ и гость; делают скриншоты.

Каждый скрипт идемпотентен: сам снимает свои сессии, отменяет свои брони и продажи,
возвращает настройки. Итог печатается последней строкой («итого: N ok, M fail»), код
выхода ненулевой при провале.

## Что нужно

- Сервер на `http://127.0.0.1:8080` со статикой `web/` (`WEB_DIR=web`), `AGENT_TOKEN` не
  задан (мок-агент подключается без токена), часовой пояс клуба Europe/Warsaw.
- Postgres `db1448` с накаченными миграциями (`backend/migrations`, как в
  `backend/entrypoint.sh`), доступ по `postgresql://u1448:p1448@127.0.0.1:5432/db1448`.
- Сид: `python3 seed_stand.py` — клуб, зоны Standard 20 zł/ч и VIP 30 zł/ч, ПК PC-01…09 и
  VIP-01…03 с координатами, владелец `boss/Boss12345`, админы `admin1|admin2/Admin12345`,
  гости `Guest06…Guest30` и `Янек`, `Яна`, `s1mple`, `Faker` (трек Ж), `Guest31…Guest50`
  (трек З) — пароль `Guest12345`, телефоны `+48500120NNN`; «Ян» из сида сервер отбивает — ник
  короче 3 символов; товары, пакеты, шаблоны смен. На чистой базе — 49 гостей.
  Скрипты рассчитывают именно на эти логины и имена. Повторный запуск сида на уже засеянной
  базе безопасен: он заводит только недостающих гостей (так стенд, засеянный до трека З,
  получает Guest31…Guest50) и ничего не перезаписывает.
- `python3` (стандартная библиотека) и `psql` в PATH; `node` ≥ 20 (в мок-агенте — встроенный
  `WebSocket`) и `npm i` в этой папке (playwright-core). Браузер — либо
  `E2E_CHROME=/путь/к/chrome`, либо `npx playwright install chromium` (тогда переменная не нужна).

## Как запускать

```bash
cd tools/e2e && npm i
python3 seed_stand.py            # на чистую базу; повторно — доведёт гостей до полного списка

./run_all.sh                     # всё (оба трека): сначала e2e_*.py, потом браузер (~12–15 минут)
./run_all.sh e2e                 # только API-наборы обоих треков
./run_all.sh pw                  # только браузерные обоих треков
./run_all.sh zh                  # только трек Ж
./run_all.sh z                   # только трек З — регрессия после каждой его итерации
./run_all.sh exits               # выходы: Esc и «назад» — киоск, PWA, админка (docs/ВЫХОДЫ-НАЗАД.md)
python3 e2e_zh6.py               # один набор — подробный вывод по каждой проверке
node pw_zh8.js
```

Переменные окружения (все со значениями по умолчанию под локальный стенд):

| переменная | по умолчанию | что это |
|---|---|---|
| `E2E_API` | `http://127.0.0.1:8080/api/v1` | адрес API; страницы и `/ws/shell` берутся от него |
| `E2E_DB` | `postgresql://u1448:p1448@127.0.0.1:5432/db1448?sslmode=disable` | строка для `psql` |
| `E2E_CHROME` | пусто | путь к Chrome/Chromium для playwright-core |
| `E2E_OUT` | системный temp | куда класть скриншоты, логи прогона и логи мок-агентов |
| `E2E_SRV_LOG` | пусто | лог сервера — для проверки «токен админа не светится в логе» (`e2e_zh0_tail`); пусто — пропуск |
| `E2E_AGENT_BIN` | пусто | агент ПК, собранный под Linux (`go build -o … ./cmd/agent`), — для связки «агент ↔ сервер» (`e2e_z20_agent`); пусто — пропуск |
| `E2E_WEB_DIR` | `../../web` | откуда брать разметку admin.html для проверок по исходнику (`pw_zh7`) |

доработке — гости закреплены:

|---|---|---|

| `e2e_booking_rules` | Guest11–Guest17 | EXCLUDE на брони, лимиты; гасит `booking_min_level` и `max_active_bookings` на время прогона |
| `e2e_zh0_tail` | Guest26 | ws-тикет, валидация депозита |
| `e2e_deposit_void`, `pw_zh1_guest` | Guest27 | **инвариант «сумма журнала кошелька = баланс»** — кошелёк Guest27 никаким другим скриптом не трогать |
| `e2e_zone_minutes`, `pw_zh2`, `pw_zh4` | Guest29 | минуты по зонам |
| `e2e_club_day`, `pw_zh1`, `pw_zh7` | Guest28 | клубные сутки; `pw_zh1` сам отменяет живые депозиты Guest28 |
| `e2e_seat_offline` | Guest28, Guest29 | офлайн-шелл, WoL, «Освободить ПК» |
| `e2e_zh5`, `e2e_zh6`, `pw_zh5`, `pw_zh6` | Guest27–Guest29 («Guest2» — нарочно неоднозначный запрос) | шторки, касса, корзина, смена |
| `e2e_zh8`, `pw_zh8` | Guest18, Guest19, Guest23, Guest24, Guest30, Янек («Ян» — два кандидата) | табло, компания, палитра, звук |
| `pw_exits_kiosk`, `pw_exits_pwa`, `pw_exits_admin` | ExitKiosk, ExitPwa, ExitAdmA, ExitAdmB — регистрируются сами при первом прогоне | выходы (`docs/ВЫХОДЫ-НАЗАД.md`): киоск за PC-06 через `?pc=`, в конце сессия гостя закрыта; админка — PC-02 и PC-07, заведённая «Проблема» закрывается |

Правила, которые дорого нарушать:

- Кошельки тестовых гостей правятся SQL только вместе с их `wallet_transactions`
  (иначе ломается инвариант из `e2e_deposit_void`).
- Проданные позиции (упавший прогон, да и каждый прогон `e2e_zh6` — расчёт долга продаёт
  насовсем) докладываются корректировкой через `POST /admin/goods/:id/stock {delta, reason:"adjust"}`,
  не SQL и не приходом: приход с З10-и4 — поставка, она ждёт цен у владельца (З18-и4ж); `e2e_zh6` делает
  это сама перед стартом — первым трём активным позициям до 30 штук.
  `pw_zh6` проданное в долг и заказ кухни отыгрывает в уборке корректировкой: остатки «Woda 0.5» и
  Lay's — как до проверки (З14-и2а; раньше каждый прогон уносил одну Woda, и 17.10 она кончилась).
- Остаток позиции SQL-ом не менять (З10-и3): у каждого движения склада — партии, остаток мимо
  склада разводит их с остатком (сверка `GET /admin/goods/lots/check` покраснеет). Вернуть остаток —
  `stock_to(gid, N, заметка)` (корректировка через API), убрать временную позицию — `drop_good(gid)`
  (вместе с движениями, партиями и поставками).
- Приход в проверках (`reason:"supply"`) — поставка «ждёт цен» (З10-и4): на стенде они копятся,
  бейдж «Бухгалтерии» у владельца и «Поставки · ждут цен» больше нуля; проверки берут число в начале
  прогона и сравнивают с ним.
- Канал персонала (`GET /admin/staff-chat`) отдаёт все непрочитанные читающего (до 500), но не меньше 100
  последних; старше — `?before=` (З15-и2). Новые искать по id, а не по длине списка: длина зависит от отметки
  «прочитано» и на долгоживущем стенде перестаёт расти. `POST /admin/staff-chat/read` без `until` — «до сейчас», как
  раньше; с `until` — до этого сообщения.
- Лента продаж смены (`GET /admin/sales`) отдаёт последние 300 строк, итоги — по всему окну суток
  (З8-и4): на долгоживущем стенде список полный, а итог сходится с базой.
- Касса — ящик клуба (З8-и1): «должно быть» у всех общее и зависит от всех наличных операций с
  прошлой сдачи — проверки считают от предпросмотра, а не от своих сумм. Сдачи
  (`shift_closeouts`) SQL не удалять: на последней стоит остаток ящика.
- Посадка требует денег хотя бы на `min_start_minutes` — «низкий баланс» моделируется
  SQL уже после старта сессии.
- `toast()` в admin.html съедает ведущий эмодзи в иконку — проверки текста тостов без него.
- Один гость в тестах = один ПК с координатами: `pickAdjacent` (компания) считает по
  `pos_x/pos_y` из сида, ряд из трёх ПК должен давать сумму расстояний 8.

## Трек З (OWNER.md)

Проверки итераций трека «Владелец после ревью 23.09»: `e2e_z<N>_<тема>.py` (API и база) и
`pw_z<N>_<тема>.js` (браузер), N — номер спринта. `run_all.sh` находит их сам по имени (по
порядку спринтов), вписывать новый скрипт никуда не нужно. Первыми идут проверки стенда
`e2e_z0_stand` и `pw_z0_stand`: упали они — дальше смотреть нечего, чинить стенд.

Скрипт пишется на помощниках — `_z.py` для API, `_z.js` для браузера — и укладывается в
30–60 строк:

```python
from _z import *
ensure_wallet("Guest31", 30)
sid = seat("Guest31", "PC-01", minutes_ago=90)   # посадка от admin1, начало сдвинуто на 90 мин назад
s, d = end(sid)
check("сессия закрыта", s == 200, J(d))
done()                                           # уборка и «Итого: ok=N fail=M», код выхода
```

Что есть в `_z.py`:

| помощник | что делает |
|---|---|
| `sql(q)`, `rows(q)`, `uid(nick)` | база через `psql`: первая строка / все строки / id по нику |
| `api(method, path, body, who)` | `(status, data)`; `who` — ник, токен из кэша процесса, на 401 — один перевход; `token=` — явный токен без перевхода (проверки отзыва) |
| `login(nick, **поля)`, `tok(nick)`, `tokens(nick)`, `jwt_claims(token)` | вход как есть, без кэша (`client="admin"` — как админка) / access из кэша, вход как админка / пара access + refresh / что внутри токена (роль, срок) |
| `check`, `near`, `section`, `J`, `at_end`, `done` | строка ok/FAIL, сравнение сумм, заголовок, короткий JSON, уборка в конце (и при падении), итог |
| `club_day(offset)`, `at_club(day, "23:50")` | клубные сутки, как их считает сервер; SQL-выражение момента по часам клуба |
| `settings()`, `set_settings(**kv)`, `restore_settings()` | настройки владельца; тронутые вернутся сами в конце |
| `wallet`, `topup`, `ensure_wallet` | кошелёк в грошах; пополнение через API (владелец, по умолчанию картой); «доложить до N zł» |
| `pcs()`, `seat`, `end`, `end_all`, `free_pcs` | ПК по имени, посадка (`minutes_ago` — сдвиг начала), завершение, уборка сессий и ПК |
| `hire_temp("z<N>adm")`, `dismiss(nick)` | временный сотрудник (пароль `Admin12345`, нанят 30 дней назад), в конце увольняется сам |
| `drawer_ready(who, floor=0)` | ящик заведён (З8-и1): на стенде без истории ящика `who` сдаёт кассу пересчётом 500 zł — начальный остаток — и снова выходит на смену; floor — «должно быть» не меньше floor zł, ниже — коррекция владельца (З18-и4в, `e2e_z8_book` — 100); → предпросмотр кассы |
| `hide_openings()`, `unhide_openings()` | остатки на начало у всех сдач — на время «ящика ещё не было»: копия — в таблице `e2e_hidden_openings` в самой базе, вернётся в конце и при падении; хвост упавшей проверки возвращается первым (З21-и3) |
| `ws_admin(ticket)`, `ws_read(sock, wait)` | live-канал админки без библиотек: апгрейд по тикету → (сокет, код ответа); события и код закрытия |
| `pin_shift(nick)` | открытая смена nick — «с сейчас» на время проверки, в конце — как была (З18-и4г): «сегодня» админа раздвигает смена, начатая раньше суток, а проверке нужны сами клубные сутки |
| `drop_good(gid)`, `stock_to(gid, N, note)` | временная позиция — SQL-ом вместе с движениями, партиями и поставками; остаток — к N корректировкой через API (З10-и3) |
| `audit(who, kind=…, day=…)`, `agent_start(pc)`, `agent_stop(name)` | строки журнала; мок агента ПК, гасится сам |

В `_z.js`: `openAdmin(nick, { viewport, timezoneId })` — Chromium 1440×900 (пояс машины), вход через форму, тур
пропущен; `nav(page,
screen)`, `shot(page, name)` → `E2E_OUT/z_<name>.png`, `text(page, sel)`; `api(method, path, body,
who)` → `{status, data}`; `sql`, `rows`, `uid`, `dropGood(gid)` (как `drop_good`), `pinShift(nick)` (как `pin_shift`),
`hideOpenings()`, `unhideOpenings()` (как `hide_openings`, `unhide_openings`), `check`, `atEnd`, `crash`;
`done()` сама добавляет проверку «ошибок JS на страницах нет».

Гости трека З приходят из сида с нулевым кошельком, без монет и опыта, зарегистрированы 60–79
дней назад: деньги, минуты, «новизну» проверка кладёт себе сама. Трек З не трогает гостей трека Ж,
трек Ж — гостей трека З.

Временные сотрудники — `z<N>adm` (N — спринт; если их в спринте несколько — своё окончание:
`z0std` у проверки стенда, `z0role` и `z0live` у проверок роли, `z0adm` у входа, `z0case` у
кейсов, `z1ch` и `z1cw` у канала персонала, `z2hire` и `z2shift` у дат, `z3in` и `z3feed` у входа, `z3pay` и `z3payw` у выплаты, `z3man` и `z3ex` у ручного табеля, `z4pack` и `z4packw` у выручки, `z14d`, `z14n`, `z14r`, `z14s`, `z14w`, `z14v` и `z14q` у увольнения, `z14l`, `z14m`, `z14j` и `z14k` у отложенного, `z14p`, `z14t` и `z14u` у паролей, `z14e` и `z14g` у стирания личных данных, `z15a` и `z15b` у графика, `z15c`, `z15r`, `z15d` и `z15e` у канала, `z15h` у прав админа, `z15t` у шаблонов смен, `z15n` у имён смен из журнала, `z15p` у переименованных шаблонов, `z15k` и `z15m` у карточки сотрудника, `z15u`, `z15v` и `z15w` у ранних периодов, `z15o` у «Сегодня отработано», `z15q` у выхода из админки, `z15s` у суток перевода часов, `z15x` и `z15y` у временного пароля, `z18j` и `z18p` у окна админа, `z18n` и `z18m` у ухода посреди смены), их заводит сама проверка через `hire_temp` / `hireTemp`. Удалить аккаунт нельзя (на нём журналы), поэтому повторный прогон
возвращает того же человека: роль admin, пароль как у admin1, карточка без увольнения. Наём с З14-и3
требует сменить пароль при первом входе — помощники снимают этот флаг SQL-ом (сам флаг — юнит и `e2e_z14_password`).
Исключение — наём «с нуля» (без даты, с экрана): `z18h` (`e2e_z18_staffdays`) и `z18hp` (`pw_z18_staffdays`)
нанимаются каждый прогон новым аккаунтом, в админку не входят и в конце удаляются SQL-ом вместе со строками журнала о
них — других ссылок на такой аккаунт нет (З18-и4е).

### Правила трека З

- Настройки — только через `set_settings`: прежние значения вернутся сами.
- Деньги гостей — через API (`topup`, продажа, расчёт), не SQL: иначе расходятся журнал
  кошелька, выручка и касса. Если без SQL никак — только вместе с `wallet_transactions`.
- Время клуба — через `club_day` и `at_club`: сессия `psql` на стенде живёт в UTC (сервер с З2-и1
  ставит своему соединению пояс клуба сам, а `psql` проверок — нет), а сутки клуба
  начинаются в `report_hour` по Варшаве.
- Неверные пароли — только на временных сотрудниках: 10 ошибок запирают ник (до З0-и3 — на 15
  минут), а `boss`, `admin1`, `admin2` нужны всем остальным проверкам.
- Смену админу открывает вход в админку (`client: "admin"`, З3-и1; до неё — любой вход). Помощники
  `tok`/`api` входят именно так, поэтому токены кэшируются; вход киоска или PWA — `login(nick)` без
  `client`. Незакрытую смену временного сотрудника закрывает его увольнение в уборке `hire_temp` (с З14-и1 —
  «закрыта увольнением», владельцу — строка в канал; что осталось открытым — уборка удаляет).
- Записи табеля временного сотрудника, которые проверка двигает сама (`e2e_z2_dates`: «забытая» смена позавчера и
  правка 09:00–21:00), удаляются все — в начале и в конце, после увольнения: запись прошлого прогона, закрытая
  увольнением, через два дня легла бы под правку (409; З15-и1а).
- Стенд первого дня — у ящика нет истории до этих суток: остатка на начало дня нет (в книге `opening_pln: null`, в
  «Raport kasowy» — «kasa jeszcze nie prowadzona», остатков после документов нет). Проверка, которой он нужен, на такой
  день проверяет эту ветку, а не падает (`e2e_z13_sheets`, З15-и1а).
- «Сегодня» админа — клубные сутки, а если его открытая смена началась раньше — с её начала (З18-и4г). Ночью admin1 на
  стенде обычно «на смене» с вечера: смену «Ночь» открыл вход прошлой проверки. Проверке, которой нужны сами клубные сутки в
  его журнале, ленте продаж или очереди кухни, — `pin_shift("admin1")` / `pinShift('admin1')`; потолок admin1 — с начала
  его окна (`from` в ответе журнала), а не с начала суток.
- Пополнение, которое проверка переносит в прошлое и потом отменяет, — картой: отмена наличного вынимает из
  сегодняшнего ящика деньги, которых в нём не было, и после нескольких прогонов «должно быть» на стенде уходит в минус —
  краснеют проверки, которые сдают с недостачей или ставят «ожидаемое + 5» (З9-и3б, З18-и4в: `e2e_z2_dates`,
  `e2e_z2_tz`, `e2e_club_day`, `e2e_deposit_void`). Проверке, которой нужен запас в ящике, — `drawer_ready(who, floor)`.
- Свои продажи проверка в уборке отменяет, даже если позицию удаляет: иначе они копятся в «Что покупают» стенда без
  себестоимости (З10-и8, З18-и4в: `e2e_z10_pricing`, `pw_z10_pricing`, как `e2e_z10_margin`).
- Строки, которые должны «отодвинуть» запись в журнале или ленте, ставить между ней и «сейчас», а не сдвигать её саму
  в прошлое: в прошлом её вытесняют события других проверок, и первая страница фильтра зависит от загрузки стенда
  (З15-и2а, `e2e_club_day`).
- «N суток назад» — как у сервера: N календарных суток по часам клуба (`AddDate`), в SQL —
  `((now() AT TIME ZONE 'Europe/Warsaw') - interval 'N days') AT TIME ZONE 'Europe/Warsaw'`;
  `now() - interval 'N days'` в сессии `psql` — ровно N×24 ч, и две недели после перевода часов граница
  съезжает на час (З16-и1г, `e2e_zh5`).
- Число месяца, которое проверка ставит «на время», не должно совпадать с сегодняшним: 31-го «поставить 31 и вернуть»
  ничего не меняет (З16-и1г, `e2e_z9_recurring`).
- «Сегодня» в проверке — клубные сутки (`club_day()`), а не дата календаря: при своём часе границы до него они ещё
  вчерашние, и сервер считает «сегодня» по ним (журнал админа, увольнение без даты). Граница суток, которую проверка
  ставит на время, — от часа прогона: в 23:xx следующего часа нет. Проверка зелёная в любой час (З18-и4а,
  `e2e_club_day`, `e2e_z2_dates`).
- Граница суток стенда — с полуночи (`report_hour` 0, З18-и4б); строки нет — тоже полночь, запасное значение в SQL
  проверок — `'0'`. Проверка, которой нужна ночь в сутках своего начала (дни перевода часов, карта загрузки), ставит
  свой час на время и возвращает: `set_settings(report_hour=8)` (`e2e_z2_dates`, `e2e_z17_hours`), в браузерной — SQL-ом
  с возвратом в `atEnd` (`pw_z17_heat`); граница стенда в конце — какая была, а не 8 (`e2e_club_day`).
- «Ночь» со своей границей — без сдвига часов: граница на два часа позже «сейчас», клубные сутки ещё вчерашние (в 23:xx
  так не сдвинуть). Календарь браузера, не совпадающий с клубным, — `openAdmin(nick, { timezoneId: 'Pacific/Kiritimati' })`
  (UTC+14). «Сегодня» «Бухгалтерии» и «Персонала» в проверке — `club_day()` / `clubDay()`: сроки регулярных, «Новый
  расход», дата документа поставки (З18-и4д, `e2e_z18_accdays`, `pw_z18_accdays`), наём, увольнение, новая запись табеля,
  «сегодня» графика (З18-и4е, `e2e_z18_staffdays`, `pw_z18_staffdays`). Проверкам смен такая «ночь» не годится: граница
  режет дневную смену стенда 08–20 (`e2e_z14_dismiss`, `pw_z14_dismiss`).
- Докладывать товар — корректировкой (`reason: "adjust"`), а не приходом: приход — поставка, она ждёт цен у владельца,
  и «Закупки» стенда копят её с каждым прогоном; приход, который проверяется сам, проверка в конце отменяет
  (`POST /admin/supplies/:id/cancel`, `e2e_z10_moves`; З18-и4ж).
- Лента с потолком («Продажи смены» — 300 последних строк, журнал — страницами): своё в ней ищется по итогам окна
  (`total_count` с ним и без него), а не среди последних строк — стенд за сутки копит строки проверок (З18-и4ж,
  `e2e_z18_journal`, `pw_z18_journal`). Тост, который ждёт проверка, — из списка тостов страницы (обёртка над `toast`),
  а не из `#toast`: тост лимитера «Слишком много запросов» перекрывает нужный (З1-и2 `pw_zh5`, З18-и4ж `pw_z16_notify`).
- Запись табеля смены, открытой входом, — датой начала смены по графику: ночная после 00:00 — вчерашними сутками.
  Проверка, которая ищет её в табеле или в сводке смены, берёт день записи, а не сегодняшние клубные сутки
  (З18-и4з: `e2e_z14_dismiss`, `pw_z14_dismiss`).
- Вёрстку под длинные числа проверка собирает сама — образцом той же функцией страницы (`repKpi`, `dlt`), а не ждёт их
  в данных стенда: данные меняются, и проверка от них то красная, то зелёная (З18-и4и: `pw_z18_kpi`).
- Пополнения задним числом — своему гостю проверки, а не общему: карточка гостя показывает 20 последних пополнений, и
  отменённые хвосты чужих прогонов вытесняют из неё своё. Свои отменённые проверка удаляет в начале и в конце (З21-и3:
  `e2e_z18_journal`, `pw_z18_journal` — гость z18jg).
- Спрятать строки стенда на время (остатки на начало у сдач) — копией в самой базе, а не в памяти проверки и не одной
  строкой SQL: стенд копит тысячи сдач, строка psql длиннее 128 КБ не запускается, а упавшая проверка уносит
  спрятанное с собой (З21-и3: `hide_openings`; `e2e_z8_book`, `e2e_z8_collect`, `e2e_z8_drawer`, `pw_z8_drawer`).
- Критерий «Готово, когда» итерации из OWNER.md — отдельной строкой `check(...)`.
