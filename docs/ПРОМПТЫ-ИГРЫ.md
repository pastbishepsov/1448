# Три промпта: трек «Игры» (запуск игр с NAS)

Три независимых пакета работ, каждый — в свой чат. Файлы не пересекаются, поэтому можно вести параллельно; коммитить после каждого пакета отдельно.

**Важно (проверено в репо 27.08.2026):** каталог игр в БД, CRUD-API, вкладка «Каталог» в админке и плитки игр в shell.html УЖЕ СУЩЕСТВУЮТ (миграции 011 + 014, `backend/internal/models/catalog.go`, `backend/cmd/server/catalog.go`, `web/admin.html` → renderCatalogTab/saveApp, `web/shell.html` → renderCatalog/launch). Агент умеет `POST /launch`. Пакеты ниже закрывают то, чего реально нет.

## Общий контракт (одинаков для всех трёх чатов)

Агент на игровом ПК, `http://127.0.0.1:1448`:
- `GET /ping` → `{status, ws_connected, computer_id, apps:[id...], lock_action}` — есть;
- `POST /launch {app_id}` → `{ok:true}` — есть; пакет 2 расширяет ответ до `{ok, pid, state}` и кодами ошибок `target_missing` / `already_running`;
- `GET /apps-status` → **новый** (делает пакет 2, потребляет пакет 3):
  `{"apps":{"cs2":{"available":true},"gta5":{"available":false,"reason":"path_unreachable"}},"running":{"app_id":"cs2","pid":1234,"since":"2026-08-27T15:00:00Z"}}`

Бэкенд: `GET /api/v1/catalog` (публичный) и `/api/v1/admin/catalog*` — есть. Пакет 1 добавляет поле обложки.

Номера миграций: пакет 1 → **054**, пакет 2 → **055** (если понадобится), пакет 3 → миграций нет.

Владение файлами: пакет 1 — `backend/migrations/054_*`, `backend/internal/models/catalog.go`, `backend/cmd/server/catalog.go`, `web/admin.html`; пакет 2 — `backend/cmd/agent/*`; пакет 3 — `web/shell.html`. Чужие файлы не трогать. `STATUS.md` не редактировать — итог писать в свой док в `docs/`.

## Промпт 2 — Агент: жизненный цикл игры (backend/cmd/agent)

```
Проект 14:48, репозиторий: C:\Users\pastbishe\Desktop\14 48\1448_project\1448 (git, main). Работаем через device_bash на моей машине.

Контекст: пилотный клуб хранит игры на сервере TrueNAS; ПК запускают их по сети (SMB-шара или iSCSI-диск — уточняется, см. docs/АУДИТ-ИГРЫ-NAS.md). Агент уже есть: backend/cmd/agent/main.go — HTTP на 127.0.0.1:1448 (/ping, /launch, /mouse-info, /mouse-accel-off, /admin-call), WS-канал к серверу (session_start/session_end/lock/wol), allowlist из agent.json + каталога сервера (runCatalog, lookupApp), очистка между гостями (cleanup.go). Прочитай это перед началом.

Задача — довести запуск игры до промышленного состояния:

1. Честный результат запуска. Сейчас startDetached() на Windows делает `cmd /C start "" <target>` — это возвращает успех, даже если exe не существует или сетевой путь недоступен: гость жмёт плитку, шелл говорит «Запускаем…», не происходит ничего. Нужно: проверять достижимость target перед запуском (для файловых путей — существование, для протоколов steam:// и подобных — своя ветка), запускать так, чтобы получать PID, и возвращать `{ok, pid, state}` либо ошибку с кодом `target_missing` / `launch_failed`.

2. Трекинг процесса. Агент должен помнить, что запущено на этом ПК (app_id, pid, время старта), отдавать это в новом эндпоинте `GET /apps-status`:
   {"apps":{"cs2":{"available":true},"gta5":{"available":false,"reason":"path_unreachable"}},"running":{"app_id":"cs2","pid":1234,"since":"..."}}
   Поле available — результат проверки доступности target (кэшируй, не дёргай сеть на каждый запрос). Этот эндпоинт потребляет гостевой экран — контракт менять только по согласованию со мной.
   Предусмотри `already_running`: повторный клик по запущенной игре не должен плодить процессы.

3. Завершение по концу сессии. Сейчас по WS-команде session_end вызывается runCleanup() — он убивает статический список имён процессов из agent.json. Запущенная игра при этом может остаться. Нужно: по session_end корректно завершать именно то, что запустил агент (сначала мягко, потом принудительно), с таймаутом, и очищать трекинг.

4. Сетевой диск (конфигурируемо, схема клуба пока неизвестна). Если игры на SMB — агент при старте должен проверить/подключить сетевой диск по настройке в agent.json (буква, UNC-путь, логин/пароль) и переподключить при потере. Если у клуба iSCSI — эта ветка просто не включается. Секреты в конфиге не логировать. Обязательно спроси меня, прежде чем закладывать конкретную схему.

5. Телеметрия (по согласованию): отправлять на бэкенд, во что играют сейчас — полезно для админки и статистики. Если делаешь — миграция строго 055_*, и опиши API в своём доке.

Ограничения:
- Go 1.26.5. Кроссплатформенность файлов _windows.go / _other.go в этом пакете уже принята — держи её, сборка под Linux не должна ломаться.
- Расширь тесты: agent_test.go, cleanup_test.go. Чистые функции выноси отдельно, чтобы тестировались без Windows.
- Обнови backend/cmd/agent/agent.example.json под новые настройки.
- Агент работает на клубных ПК без интернета до бэкенда в момент старта — не блокируй запуск игры недоступностью сервера.
- `GIT_OPTIONAL_LOCKS=0 git status` на маунте; коммит предлагай мне, сам не пушь (пуш в main пересобирает демо-стенд Railway).
- Не трогай web/shell.html, web/admin.html, backend/cmd/server/* — над ними идёт параллельная работа.

Итог: док docs/АГЕНТ-ЗАПУСК-ИГР.md (что делает агент, все настройки agent.json, коды ошибок, как проверить на живом ПК) и готовые к коммиту изменения.
```
