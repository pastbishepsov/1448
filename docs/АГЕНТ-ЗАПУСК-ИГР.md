# Агент: жизненный цикл игры

Пакет 2 трека «Игры» (см. `docs/ПРОМПТЫ-ИГРЫ.md`). Файлы: `backend/cmd/agent/`.
Соседние пакеты — каталог (`docs/КАТАЛОГ-ИГР.md`) и витрина (`docs/ВИТРИНА-ИГР.md`).

## Зачем

Раньше запуск игры был «выстрелом в темноту»: `cmd /C start "" <target>` возвращает
успех всегда — и когда exe нет, и когда сетевой диск отвалился. Гость жал плитку,
видел тост «Запускаем…» и не получал ничего. Агент не знал, что на ПК запущено,
и по концу сессии убивал только статический список имён из конфига — сама игра
переживала гостя.

Теперь агент проверяет путь до запуска, получает PID, помнит запущенное, отдаёт
это витрине и корректно закрывает по концу сессии.

## HTTP-контракт (127.0.0.1:1448)

### `POST /launch` — запустить

Запрос: `{"app_id": "cs2"}`

| Ответ | HTTP | Тело |
|---|---|---|
| Запущен прямой exe | 200 | `{"ok":true,"app_id":"cs2","pid":4231,"state":"running"}` |
| Отдан обработчику (steam:// и т. п.) | 200 | `{"ok":true,"app_id":"cs2","pid":0,"state":"starting"}` — или `"launched"`, если у записи нет `process` |
| Уже работает | 200 | `{"ok":true,"app_id":"cs2","pid":4231,"state":"already_running","code":"already_running"}` |
| Нет `app_id` | 400 | `{"code":"invalid_request"}` |
| Не в allowlist | 404 | `{"code":"unknown_app"}` |
| Диск/шара не отвечает | 409 | `{"ok":false,"code":"path_unreachable","reason":"path_unreachable","message":"Диск с играми сейчас недоступен"}` |
| Диск на месте, файла нет | 409 | `{"ok":false,"code":"target_missing","reason":"target_missing","message":"Игра не установлена на этом компьютере"}` |
| Система не смогла запустить | 500 | `{"ok":false,"code":"launch_failed","message":"…"}` |
| Не POST | 405 | `{"code":"method"}` |

`state` — из того же словаря, что и в `/apps-status`: `running` · `starting` ·
`launched` (плюс `already_running`). Витрина по `state: "running"` зажигает плитку
«запущена» сразу, не дожидаясь следующего опроса.

`reason` — точная причина отказа: `path_unreachable` (корень тома или шары не
отвечает), `target_missing` (диск на месте, файла нет), `no_target` (в каталоге
пустой путь). **`code` повторяет причину**, потому что витрина
(`web/shell.html`, таблица `NA_REASON`) выбирает текст гостю именно по `code`:
если «шара не отвечает» приедет общим `target_missing`, гость прочитает «игра не
установлена» и пойдёт искать её сам вместо того, чтобы позвать администратора.
Единственное отличие: `no_target` уезжает как `target_missing` — для гостя это
одно и то же. `message` уже на русском и готов к показу как есть.

### `GET /apps-status` — доступность и что запущено

**Этот контракт потребляет гостевая витрина `web/shell.html`. Менять — только по
согласованию с владельцем проекта.**

```json
{
  "apps": {
    "cs2":  {"available": true,  "kind": "protocol"},
    "gta5": {"available": false, "reason": "path_unreachable", "kind": "file",
             "checked_at": "2026-08-27T15:00:00Z"},
    "new":  {"available": true,  "reason": "checking", "kind": "file"}
  },
  "running": {"app_id": "cs2", "pid": 4231, "since": "2026-08-27T15:00:00Z", "state": "running"},
  "running_all": [
    {"app_id": "cs2", "pid": 4231, "since": "2026-08-27T15:00:00Z", "state": "running"}
  ]
}
```

- `running` — **последняя запущенная живая** запись или `null`. `running_all` —
  все, свежайшая первой (гость может держать Discord рядом с игрой); витрина
  вправе игнорировать это поле.
- `state` записи: `running` (есть живой PID) · `starting` (протокол запущен, ждём
  появления процесса по имени) · `launched` (запущено, PID узнать неоткуда).
- `reason: "checking"` при `available: true` — путь ещё не проверяли (первые
  секунды после старта агента). Оптимизм осознанный: лучше честная ошибка на
  клике, чем ложно погашенная плитка. Ошибётся — гость увидит `target_missing`.
- Отвечает **из кэша**: в сеть на запросе не ходит никогда, поэтому мёртвая шара
  не подвешивает витрину. Проверка идёт фоном раз в `check_interval_sec`.

### `GET /ping` — без изменений

Список `apps` теперь берётся из того же объединённого allowlist, что и
`/apps-status` (локальный `agent.json` главнее каталога сервера).

## Настройки `agent.json`

### Блок `launch` (новый)

| Ключ | По умолчанию | Границы | Что делает |
|---|---|---|---|
| `check_interval_sec` | 60 | 5…3600 | период фоновой проверки путей; он же TTL кэша |
| `check_timeout_sec` | 5 | 1…60 | таймаут одной проверки пути (зависший SMB не держит агента) |
| `attach_timeout_sec` | 60 | 1…600, отрицательное = не ждать | сколько ждать процесс по имени после протокольного запуска |
| `stop_timeout_sec` | 10 | 1…120 | сколько ждать после мягкого закрытия до принудительного |
| `watch_interval_sec` | 3 | 1…60 | период опроса живости запущенных процессов |
| `stop_on_session_end` | `true` | — | гасить по концу сессии то, что запустил агент |
| `telemetry` | `true` | — | слать `app_launch` / `app_exit` на бэкенд по WS |

Отдельно, вне блока `launch`: **`games_root`** — корень игр этого ПК, если он
отличается от клубного (см. ниже «Своя буква диска»). Пусто = обычный случай.

`0` в числовом поле = «взять дефолт», поэтому пустой блок `launch` (или его
отсутствие) работает правильно. Опечатка вроде `check_interval_sec: 1` зажимается
до 5 — проверка сети раз в секунду клубу не нужна.

### Записи в `apps` (два новых поля)

```json
"cs2": {
  "name": "CS2",
  "target": "G:\\Games\\…\\cs2.exe",
  "args": [],
  "dir": "G:\\Games\\…\\win64",
  "process": "cs2.exe"
}
```

- `dir` — рабочая папка процесса. Пусто = папка самого exe (многие игры иначе не
  находят свои ресурсы).
- `process` — **имя процесса игры**. Нужно там, где PID запуска игре не
  принадлежит:
  - `target` — протокол (`steam://rungameid/730`): Windows отдаёт ссылку Steam,
    игру запускает он. Агент ждёт появления `process` до `attach_timeout_sec`,
    берёт настоящий PID и дальше ведёт игру как обычно.
  - `target` — лаунчер, который закрывается после старта игры (Riot Client →
    VALORANT). Когда PID лаунчера умирает, агент проверяет `process` и
    подхватывает эстафету.
  - Побочный плюс: если игра уже работает (гость поднял её мимо витрины), клик по
    плитке вернёт `already_running` и агент возьмёт этот процесс под контроль —
    значит, закроет по концу сессии.

  Без `process` протокольный запуск остаётся в состоянии `launched`: агент честно
  говорит, что PID неизвестен, и по концу сессии такую игру добивает только
  список `cleanup.kill`.

Те же поля можно завести и в каталоге на сервере — агент читает `target`/`args` из
`/api/v1/catalog`; `dir` и `process` пока приходят только из локального
`agent.json` (в каталоге таких колонок нет — при необходимости это пакет 1).

## Сопряжение с витриной

`web/shell.html` (пакет 3) опрашивает `/apps-status` раз в 20 с в покое и раз в
2.5 с пока ждёт запуск, а отсутствие эндпоинта (404/501 от старого агента)
переносит молча — витрина от этого не ломается. Из ответа она читает `apps` и
`running.app_id`; `running_all` игнорирует. Плитка гаснет только по
`available === false`, поэтому непроверенное (`reason: "checking"`) остаётся
активным. Обратная совместимость держится в обе стороны: новый агент со старой
витриной работает как раньше, новая витрина со старым агентом — тоже.

## Конец сессии

По WS-команде `session_end` агент делает **два шага в этом порядке**:

1. `stopTracked()` — закрывает то, что запустил сам: сперва мягко
   (`taskkill /PID <pid> /T` — окнам дерева процессов уходит WM_CLOSE, игра
   успевает сохраниться), ждёт до `stop_timeout_sec`, затем принудительно
   (`taskkill /PID <pid> /F /T`). Итог по каждому пишется в лог: «закрылось само» /
   «закрыто принудительно» / «НЕ закрылось». Реестр очищается.
2. `runCleanup()` — прежняя очистка между гостями по `cleanup` (Г9-и4). Не
   изменилась.

Порядок важен: сначала своё по PID, потом общий добой по именам.

## Пауза и AFK: `lock` / `unlock` (К0-и1, KIOSK.md Р1)

Пауза гостя, пауза с телефона и AFK-автопауза приходят агенту **не** как
`session_end`, а как отдельная команда:

```json
{"type":"lock",   "payload":{"session_id":"…","reason":"paused","by":"guest"}}
{"type":"lock",   "payload":{"session_id":"…","reason":"afk","by":"afk"}}
{"type":"unlock", "payload":{"session_id":"…","resumed":true}}
```

На `lock` агент делает только `applyLockAction()` (по `lock_action` из
`agent.json`) — запущенная игра **живёт**, реестр не трогается, очистка не
запускается; на `unlock` ничего, кроме записи в лог. Закрыть игру и вычистить
профиль может только настоящий `session_end`. До этой итерации сервер слал на
паузе `session_end`, и агент закрывал матч гостя (`stop_on_session_end`).

Честная оговорка: с `lock_action: none` (дефолт) пауза запирает только
браузерный гостевой экран — окно игры остаётся доступным через Alt+Tab, и
единственный ограничитель — лимит паузы `pause_limit_min` (по его исчерпании
сервер снимает паузу сам, время идёт). Полноценно запирает C#-киоск
(HardLock поверх всего) или `lock_action: kiosk`; `lock_windows` не
рекомендуется — снять его сможет только тот, кто знает пароль Windows.

Совместимость: старый агент на `lock` пишет «Неизвестная команда» и экран не
запирает вовсе, поэтому **сервер и агент выкатываются вместе**.

## Состояние сессии: `state` в ответ на каждый `session_tick` (К4-и1, KIOSK.md №13)

Команды `session_start` / `session_end` / `lock` / `unlock` идут по живому
сокету best-effort. Если WS лежал ровно в момент завершения сессии, агент
оставался с открытой игрой гостя и без очистки между гостями — следующий
садился в чужой матч. Теперь на **каждый** `session_tick` сервер отвечает
истиной о сессии этого ПК, а агент шлёт первый тик сразу после (ре)коннекта:

```json
{"type":"state","payload":{"session_active":true,"paused":true,"session_id":"…","reason":"afk"}}
{"type":"state","payload":{"session_active":false,"paused":false,"session_id":null}}
```

Агент сверяет `state` с тем, что знал сам и что держит в реестре
(`reconcile`, `cmd/agent/state.go`):

| Сервер говорит | Агент знал / держит | Действие |
|---|---|---|
| сессии нет | держит запущенную игру **или** знал «сессия идёт» | как `session_end`: закрыть запущенное + очистка (один раз) |
| сессии нет | ничего не знал, реестр пуст | ничего |
| сессия идёт | не знал / другая `session_id` | как `session_start` (пропущен старт) |
| пауза | не были на паузе | как `lock` (экран заперт, игра живёт) |
| не пауза | были на паузе | как `unlock` |

Команды сервера двигают то же «знание», поэтому `state` после уже
выполненного `session_end` очистку второй раз не запускает
(`TestReconcile`, `TestStateKeeperOnce`). C#-сервис (`Worker.cs`) делает то
же на своей машине состояний: догоняет `session_start`/`session_end`, на
паузе шлёт App `Lock` с причиной, иначе `Unlock`. Старый агент на `state`
пишет «Неизвестная команда» — не ломается.

## Уведомления поверх игры: `POST /notify` (К4-и2, KIOSK.md №28)

Гость в матче не видит экран киоска. Гостевой экран дублирует агенту
**критичные** тосты — деньги (`balance_low/zero`), бронь
(`booking_soon/deadline/reminder`), кухня (`delivering/done`), ответ админа,
`pause_over`, `afk_warn`, `ready_auto`, пересадка, очередь на ПК:

```
POST http://127.0.0.1:1448/notify
{"title":"14:48","text":"⏳ Через 5 мин закончатся деньги","kind":"balance_low"}
→ {"ok":true,"shown":true}
```

Агент показывает системный тост Windows — WinRT `ToastNotification` через
встроенный PowerShell (`notify_windows.go`): без BurntToast и других модулей,
без регистрации приложения (отправитель по умолчанию — AUMID PowerShell,
`notify.app_id` в `agent.json` меняет его; `notify.enabled:false` выключает).
Текст уже локализован словарями шелла — агент его не знает. Заголовок ≤ 60
символов, текст ≤ 200, не чаще раза в 1,5 с; не на Windows — строка в лог.
`GET /ping` отдаёт `notify: true/false`.

**Честно про полноэкранные игры:** эксклюзивный fullscreen Windows тосты
прячет (Focus Assist / игра владеет экраном) — гость их увидит, выйдя по
Alt+Tab; borderless и оконный режим показывают тост поверх игры. Внутри
C#-киоска шелл шлёт `nativePost({cmd:'notify'})`, и строка появляется в
OverlayWindow под XP-виджетом на 8 секунд — этот путь полноэкранность не
ломает.

## Токен агента: `AGENT_TOKEN` (К4-и3, KIOSK.md)

Закрывает дыру 26.08: `/ws/shell` пускал любого, кто знает UUID компьютера
(он есть в публичном `/clubs/:id/computers`), а `/catalog` отдавал пути к
играм на диске, аргументы и `games_root` каждому, кто открыл адрес сервера.

Один секрет на клуб — `AGENT_TOKEN` на сервере (`.env.club`, Railway) и тот же
токен в конфигах на каждом ПК: `agent.json` → `"token"`, `appsettings.json` →
`Shell:AgentToken`, `shell.json` → `"agent_token"` (C#-киоск сам тянет
каталог для allowlist). Агент шлёт его заголовком `X-Agent-Token` — на WS и
на `GET /catalog?full=1`; без верного токена сервер отвечает `401
agent_token_invalid`, агент пишет в лог «сервер не принял токен» и повторяет
раз в 30 с. Публичный `/catalog` (гостевой экран) теперь без путей на диске,
аргументов, `target_raw` и `games_root`; ссылки и протоколы (`steam://…`,
`https://…`) остаются — по ним киоск запускает без агента.

Порядок обновления в клубе: (1) раздать токен по ПК, (2) задать `AGENT_TOKEN`
на сервере. Пустой `AGENT_TOKEN` = проверка выключена (сервер пишет
предупреждение при старте) — агенты без токена продолжают работать, чтобы
обновление сервера не оставило клуб без агентов.

## Сенса в игру: `sens` в `agent.json`, `sens_apply` и `1448.cfg` (К7 → С2, SENS.md)

Профиль сенсы гостя (DPI + сенса по играм, `GET /me/sensitivity`) едет за ним
на любой ПК сети: гость садится — и CS2 стартует с его сенсой. Делает это
агент, файлами на ПК, с бэкапом и откатом; сервер присылает профиль уже
пересчитанным под DPI мыши клуба.

**Инвариант — cm/360, а не пара dpi+sens (С2-и1, Р2/Т4).** Мыши в клубе
одинаковые, DPI — свойство ПК; настройка `mouse_dpi` в админке («Мышь
клуба: DPI», 0 = не задан). Сервер отдаёт агенту `sens × dpi_профиля /
mouse_dpi` и добавляет `rescaled_from` (пример: профиль 2.0 @1600 → на ПК
4.0 @800 — cm/360 тот же). Гость со своей мышью говорит об этом в студии
(«Со своей мышью» → `own_mouse`), тогда без пересчёта.

**Кто просит.** Три пути к одному `sensApplier.apply` (`sens.go`):

- сервер — в `session_start` (и при пересадке) кладёт
  `"sens": {"dpi": 800, "games": {"cs2": 4, "apex": 2, …}, "rescaled_from": 1600}`,
  если у гостя сохранён профиль с играми (`sensPayloadFor` в
  `sensitivity.go`); нет профиля — поля нет, агент молчит;
- сервер — команда `sens_apply {dpi, games}` (С2-и4, Т5): гость сохранил
  профиль во время сессии (`PUT /me/sensitivity` при активной сессии на ПК,
  который на связи). Агент применяет и отвечает по тому же WS
  `sens_result {applied, skipped, dry_run, running}`; сервер превращает его в
  уведомление гостю `sens_applied` — тост в киоске, в PWA и поверх игры.
  Кнопки «Применить в игре» и запроса браузером в `127.0.0.1` больше нет
  (в киоске её не было, а Chromium ограничивает запросы к локальной сети);
- curl-проверка на живом ПК:

```
POST http://127.0.0.1:1448/sens-apply
{"dpi":800,"games":{"cs2":2.5,"apex":1.4,"valorant":0.35,"quake":2}}
→ 200 {"applied":["apex","cs2"],
       "skipped":{"valorant":"cloud","quake":"unsupported"},
       "dry_run":false,"running":[],"supported":["apex","cs2"],"cs2_mode":"exec"}
```

| Ситуация | Код | Ответ |
|---|---|---|
| Выключено в `agent.json` (`sens.enabled=false`) | 409 | `{"code":"sens_disabled","message":"Подстановка сенсы на этом ПК выключена (agent.json → sens.enabled)"}` |
| Нет `games` | 400 | `{"code":"bad_request","message":"Нужны games {игра: сенса}"}` |
| Не POST | 405 | `{"code":"method"}` |

Причины в `skipped`: `cloud` — настройки игры в облаке (Valorant → Riot), у
ПК нет файла, который стоит трогать; `unsupported` — игру не умеем
(OW2/CoD/Quake/Deadlock — до проверки формата их конфигов на живом ПК);
`no_config` — игру умеем, но конфига/папки игры на этом ПК нет; `disabled`
— `sens.enabled=false` (по WS-команде); `error` — файл не прочитался/не
записался (детали в логе агента). `running` — игра уже запущена: подхватит
при перезапуске (CS2 — ещё и по `exec 1448` в консоли).

`GET /ping` отдаёт `sens: true/false`, `sens_games: ["apex","cs2"]`,
`sens_mode: exec|vcfg` и `sens_current` (С2-и2) — что стоит в играх на этом
ПК прямо сейчас: `{"cs2": {"sens": 2.75, "res_w": 1280, "res_h": 1024,
"aspect": "5:4", "aspect_mode": 0}, "apex": {"sens": 2}}`. Аккаунт Steam — из
`config/loginusers.vdf` (`MostRecent "1"` → SteamID64 − 76561197960265728 =
папка `userdata\<id>`), нет файла — самый свежий vcfg; разрешение — из
`cs2_video.txt` рядом с vcfg. Студия показывает «В CS2 на этом ПК сейчас N —
взять» и отдаёт aspect калибратору.

**Что и куда пишем.**

| Игра | Режим | Файл | Как |
|---|---|---|---|
| CS2 | `exec` (по умолчанию, С2-и3, Р1/Т2) | `<CS2>\game\csgo\cfg\1448.cfg` — `// 14:48 …` + `sensitivity "2.5"` | наш файл; запуск CS2 идёт с `+exec 1448` (`withSensArgs` в `launch.go`: `steam://rungameid/730` → `steam://run/730//+exec%201448/`, exe — аргумент `+exec 1448`; C#-киоск — `shell.json` `sens_exec: true`). Работает под ЛЮБЫМ Steam-аккаунтом и не зависит от момента входа в Steam: на `session_start` гость в Steam ещё не вошёл, и «самый свежий userdata» К7 попадал в чужую папку. Файл живёт всегда: с сенсой после `session_start`/`sens_apply`, пустой (один комментарий) после `session_end` и на старте агента |
| CS2 | `vcfg` (К7, запасной) | `<Steam>\userdata\<id>\730\local\cfg\cs2_user_convars_0_slot0.vcfg` (Valve KeyValues) | `vcfgSetConvar`: меняется ТОЛЬКО значение `"sensitivity"` внутри блока `"convars" { … }`, ключ без учёта регистра, CRLF/LF и отступы как в файле; ключа нет — первой строкой блока; файл пуст — структура целиком |
| Apex | — | `%USERPROFILE%\Saved Games\Respawn\Apex\local\settings.cfg` | `apexCfgSet`: строка `mouse_sensitivity "1.4"`; ключа нет — в конец |

Значение — `formatSens`: до четырёх знаков, без хвостовых нулей (`2.5`,
`2`, `0.8125`). То же значение уже стоит — файл не трогаем.

**Где искать.** `steam_dir` пусто → `%ProgramFiles(x86)%\Steam`,
`%ProgramFiles%\Steam`, `C:\Program Files (x86)\Steam`. Корень CS2 (`cs2_dir`
пусто) — `<Steam>\steamapps\common\Counter-Strike Global Offensive` у корня
Steam и у каждой библиотеки из `steamapps\libraryfolders.vdf`. Явные
`cs2_dir` / `cs2_cfg` / `apex_cfg` главнее поиска — задать их, если Steam
стоит нестандартно или конфиг лежит в профиле другого пользователя Windows.

**Откат — обязательный (Т3).** В exec-режиме на первой записи в сессии ВСЕ
существующие vcfg CS2 (`userdata\*\730\local\cfg\…`) копируются в
`<файл>.1448bak` — CS2 при выходе пишет сенсу в vcfg текущего аккаунта, и
клубный аккаунт иначе унаследовал бы её; аккаунт гостя, появившийся во время
сессии, в бэкапах не был — его не трогаем (сенса, которую он сам сохранил у
нас, остаётся его). В vcfg-режиме и для Apex — бэкап перед ПЕРВОЙ записью в
файл; повторные записи той же сессии бэкап не перезаписывают (в нём всегда
оригинал). На `session_end` (в `onSessionEnd`, после общей очистки) и на
старте агента (упал посреди сессии) бэкапы возвращаются на место и
удаляются, `1448.cfg` пустеет — лог «сенса: после сессии возвращено
конфигов: N» / «на старте возвращено конфигов из бэкапа: N». Следующий гость
не унаследует чужую сенсу, профиль клубного аккаунта не «расползается».

**Блок `sens` в `agent.json`:**

| Ключ | По умолчанию | Что |
|---|---|---|
| `enabled` | `false` | подставлять ли вообще; выкл — `/sens-apply` отвечает 409, `session_start` и `sens_apply` игнорируются (`skipped: disabled`) |
| `dry_run` | `true` | только лог «сенса [пробный режим]: cs2 — записал бы sensitivity 2.5 в …», файлы и бэкапы не трогаем; боевой режим владелец включает после сухого прогона на пилотном ПК |
| `cs2_mode` | `"exec"` | `exec` — 1448.cfg + `+exec 1448` в запуске; `vcfg` — запись в vcfg самого свежего аккаунта (К7) |
| `cs2_dir` | `""` | корень CS2; пусто — ищем по Steam и его библиотекам |
| `steam_dir` | `""` | корень Steam; пусто — стандартные пути |
| `cs2_cfg` | `""` | явный путь к `cs2_user_convars_0_slot0.vcfg` (vcfg-режим и чтение `sens_current`) |
| `apex_cfg` | `""` | явный путь к `settings.cfg` Apex |

Порядок включения на пилотном ПК: в админке «Мышь клуба: DPI» = DPI клубных
мышей → `enabled:true, dry_run:true` → сесть гостем с профилем → в логе
агента «записал бы sensitivity … в …\game\csgo\cfg\1448.cfg (+ бэкап N vcfg)»
с верными путями → `dry_run:false` (и в C#-киоске `shell.json`
`sens_exec: true`) → сессия → `1448.cfg` с сенсой, `.1448bak` у всех vcfg →
запустить CS2 из шелла → в консоли CS2 `sensitivity` = значение профиля
(это и есть проверка, что `+exec` из параметров запуска перекрывает vcfg) →
сохранить сенсу в студии → тост «🎮 Сенса на этом ПК: CS2» → `session_end`
→ `1448.cfg` пустой, vcfg как были, `.1448bak` исчезли.

**Честно про ограничения.**

- *Порядок применения в CS2.* `+exec` из параметров запуска выполняется
  после загрузки vcfg — проверить на пилотном ПК (консоль CS2, см. выше).
  Если у клуба есть свой `autoexec.cfg` со строкой `sensitivity`, он
  перекроет нашу — убрать её оттуда.
- *Steam Cloud Sync.* В exec-режиме vcfg мы не пишем, а `local\cfg` в облако
  не синкается — оговорка К7 теряет остроту; бэкап/откат vcfg всё равно на
  месте.
- *Игра уже запущена* — CS2 подхватит новую сенсу при перезапуске или по
  `exec 1448` в консоли (тост так и говорит); Apex — при следующем старте.
- *Valorant* — только руками, студия так и говорит («облако Riot»).
- *C#-киоск* — тот же порт в `Shell1448.Service/SensApplier.cs`
  (`Sens*` в `appsettings.json`, по умолчанию выключено и пробный режим;
  `SensCs2Mode`, `SensCs2Dir`), запуск с `+exec` — `Shell1448.App`
  (`shell.json` `sens_exec`, `Shell1448.Shared/SensLaunch.cs`); собирается
  CI на Windows, проверка на пилотном ПК отдельно. `running` сервис не
  знает (игры запускает App) — в его `sens_result` всегда пусто.

## Телеметрия

Агент шлёт в существующий WS-канал (`/api/v1/ws/shell`) два типа сообщений:

```json
{"type":"app_launch","payload":{"app_id":"cs2","pid":4231,"target_kind":"file",
                                "computer_id":"…","at":"2026-08-27T15:00:00Z"}}
{"type":"app_exit","payload":{"app_id":"cs2","pid":4231,"duration_sec":3600,
                              "reason":"session_end","computer_id":"…","at":"…"}}
```

`reason` в `app_exit` есть только при закрытии по концу сессии; обычный выход
игры его не несёт. Отправка идёт отдельной горутиной и никогда не блокирует
запуск: нет связи с бэкендом — событие просто теряется, игра всё равно стартует.

**Серверная часть сознательно не сделана в этом пакете** (файлы
`backend/cmd/server/*` заняты параллельной работой). Сейчас хаб логирует
`app_launch`/`app_exit` как неизвестный тип и ничего не ломает
(`internal/websocket/hub.go`, `handleMessage` → `default`). ТЗ для следующего
захода:

- миграция **`055_create_app_sessions.sql`** (номер зарезервирован за этим треком):
  `app_sessions(id, club_id, computer_id, user_id NULL, app_id TEXT, pid INT,
  started_at, ended_at NULL, duration_sec NULL, end_reason TEXT NULL)`, индексы по
  `(club_id, started_at)` и `(computer_id, ended_at)`;
- в `hub.handleMessage` — две ветки: `app_launch` открывает строку, `app_exit`
  закрывает по `(computer_id, app_id, pid)`; незакрытые строки закрывать по
  дисконнекту ПК, иначе после жёсткой перезагрузки они висят вечно;
- `GET /api/v1/admin/app-stats?from=&to=` — топ игр по времени и по запускам;
  на живом экране админки «во что играют сейчас» можно брать прямо из хаба, без БД.

Выключается на стороне ПК: `"launch": {"telemetry": false}`.

## Где лежат игры: локальный диск, монтировать нечего

**Ответ разведки (31.08.2026, `docs/РАЗВЕДКА-РЕЗУЛЬТАТ.md`): игры запускаются с
ЛОКАЛЬНОГО диска `D:` каждого ПК** (6.6 ТБ, почти всё под `D:\online\`). Не
сеть, не iSCSI, не diskless. Сетевая шара `\\192.168.123.97\share` (Z:) на ПК
**отсоединена** — это мастер и источник обновлений на отдельной подсети, а не
путь запуска.

**Поэтому агент ничего не монтирует и монтировать не будет.** Прежний пункт
«когда аудит ответит SMB — добавить блок `network_drive` и звать `net use`»
снят: он относился к схеме, которой в клубе нет. Обновление игр с мастера —
задача синхронизации и регламента с админом клуба (Фаза 4 в
`docs/ПЛАН-ПЕРЕЕЗДА.md`), она не лежит на пути запуска игры и агента не
касается. Если такой клуб когда-нибудь появится, монтирование останется
внешним по отношению к агенту: диск подключает система, агент видит готовый
путь.

Что при этом всё равно работает: если чей-то `target` окажется на сетевом пути
(`\\nas\games\…` или подключённой букве), агент **видит его отвал** — проверка
достижимости отличает «шара не отвечает» (`path_unreachable`) от «файла нет»
(`target_missing`), и гость получает внятное «Диск с играми сейчас недоступен»
вместо тишины.

### Своя буква диска на отдельном ПК: `games_root`

Клубный корень задаётся один раз в админке (`games_root`, кнопка «Корень игр»),
и сервер отдаёт агенту `target` уже развёрнутым — на пилоте это `D:\online`.
Но буква — свойство конкретного ПК. Если на каком-то из них игры лежат, скажем,
на `E:\online`, в его `agent.json` ставится

```json
"games_root": "E:\\online"
```

и агент разворачивает шаблон `target_raw` (сервер шлёт его рядом с `target`)
своим корнем — сам, без правок на сервере и не задевая остальные ПК. Пусто
(обычный случай) — берётся готовый `target` от сервера. Подстановка идёт и в
`args`. Это ровно то требование к пакету П2, что описано в
`docs/КАТАЛОГ-ИГР.md` §2.

## Как проверить на живом ПК

Сборка Windows-exe (из корня репо):

```
docker compose run --rm --no-deps -e GOOS=windows -e GOARCH=amd64 \
  backend go build -o bin/shell-agent.exe ./cmd/agent
```

Дальше `backend/bin/shell-agent.exe` рядом с `agent.json` на клубном ПК. В
консоли агента видно всё: `▶` — запуск, `■` — завершение, `⛔` — конец сессии,
`✗` — отказ.

1. **Живой ли агент.** `curl.exe http://127.0.0.1:1448/ping` → в `apps` должны
   быть id из `agent.json` и из каталога сервера.
2. **Доступность.** `curl.exe http://127.0.0.1:1448/apps-status` — сразу после
   старта часть игр будет с `"reason":"checking"`, через несколько секунд
   заменится реальным вердиктом. Игры на несуществующем пути должны стать
   `"available": false`.
3. **Отвал сетевого диска — главный сценарий клуба.** Отключите шару
   (`net use G: /delete` или выдерните NAS из сети), подождите
   `check_interval_sec` и повторите шаг 2: у игр с этого диска должно появиться
   `"reason":"path_unreachable"`. Клик по такой плитке обязан вернуть 409, а не
   «Запускаем…»:
   `curl.exe -X POST -H "Content-Type: application/json" -d "{\"app_id\":\"cs2\"}" http://127.0.0.1:1448/launch`
4. **Честный запуск.** Верните диск, запустите игру той же командой — в ответе
   должен быть `"state":"started"` и ненулевой `pid`. Сверьте PID с диспетчером
   задач.
5. **Трекинг.** `curl.exe http://127.0.0.1:1448/apps-status` → в `running` тот же
   `app_id` и `pid`, `state: running`.
6. **Повторный клик.** Тот же POST /launch → `"state":"already_running"`, тот же
   `pid`, второго процесса в диспетчере не появилось.
7. **Протокол.** Для записи с `target: steam://…` и заданным `process` ответ будет
   `"state":"launched"`, `pid: 0`; через 10–40 секунд (Steam думает) в
   `/apps-status` появится настоящий PID и `state: running`.
8. **Закрытие игры вручную.** Закройте игру — не позже `watch_interval_sec`
   запись должна исчезнуть из `running`, в логе появится `■ … завершилось`.
9. **Конец сессии.** Завершите сессию из админки. В логе — блок `⛔` с итогом по
   каждому процессу; игра закрыта, `running` пуст.

Проверка без клуба: `go test ./cmd/agent` — сценарий «запуск → PID → повторный
клик → session_end» гоняется на живом процессе в `TestLaunchTrackStop`.

## Границы и известные ограничения

- **Античиты.** Игры с ядерными античитами (Vanguard, FACEIT) не любят
  принудительное завершение из-под другого процесса. Для них имеет смысл держать
  запас по `stop_timeout_sec` и полагаться на мягкую фазу.
- **`already_running` без PID.** Протокольный запуск, у которого не задан
  `process`, отслеживается только как «запущено» — повторный клик по нему
  сделает ещё один вызов обработчика. Это безопасно: Steam/Riot второй копии не
  поднимут, они просто вынесут окно вперёд.
- **PID может быть переиспользован** системой после смерти процесса — окно между
  смертью и опросом (`watch_interval_sec`, 3 c) теоретически позволяет принять
  чужой процесс за игру. Практического значения на клубном ПК не имеет.
- **Запуск не блокируется недоступностью бэкенда.** Каталог, WS и телеметрия —
  всё best-effort: агент стартует и запускает игры из локального `agent.json`,
  даже если сервер лежит.
- Кроссплатформенность сохранена: `proc_windows.go` / `proc_other.go`; вся логика
  в `launch.go` — чистые функции с инъекцией системных вызовов, поэтому
  собирается и тестируется на Linux (CI).
